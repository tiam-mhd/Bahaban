# بهابان

نمونهٔ اولیهٔ فارسی برای ثبت کالاها، دریافت قیمت‌نامهٔ تأمین‌کنندگان، بازبینی تطبیق‌ها و اعمال کنترل‌شدهٔ قیمت خرید.

## امکانات

- ورود یکپارچه با شمارهٔ موبایل ایران و کد یک‌بارمصرف؛ نشست در کوکی `HttpOnly`، با `Secure` در تولید.
- چند کسب‌وکار و چند شعبه برای هر کاربر؛ هر کسب‌وکار با یک شعبهٔ اصلی ساخته می‌شود. داده‌ها و تنظیمات به شعبه محدودند.
- ثبت دستی و ورود کالا و تأمین‌کننده؛ ورود CSV/XLSX با نگاشت ستون‌ها، پیش‌فرض ۵ مگابایت، ۲٬۰۰۰ ردیف و ۸۰ ستون.
- پیش‌نمایش موقت؛ فایل اصلی ذخیره نمی‌شود. مقادیر استخراج‌شده در ردیف‌های قیمت‌نامه نگه‌داری می‌شوند تا بازبینی ممکن باشد.
- تطبیق به‌ترتیب بارکد، SKU و نام؛ قیمت فعلی تا تأیید صریح کاربر تغییر نمی‌کند.
- تأیید گروهی تراکنشی، بررسی نسخه/قیمت قبلی، تاریخچه و رخدادهای حسابرسی.
- پیشنهاد جداگانهٔ حاشیهٔ سود ناخالص و افزایش روی بهای خرید؛ هیچ‌کدام قیمت فروش را خودکار تغییر نمی‌دهند.
- خروجی عمومی CSV/XLSX از ردیف‌های تأییدشده، همراه با محافظت در برابر فرمول‌های صفحه‌گسترده.
- رابط RTL واکنش‌گرا، فونت خودمیزبان Vazirmatn و endpoint سلامت در `/api/health`.

PDF، OCR، دعوت همکاران، مدیریت تیم و پنل مدیر سراسری در این نسخه فعال نیستند. برای فایل اسکن‌شده، ردیف‌ها باید از CSV/XLSX قابل بررسی تهیه شوند. دادهٔ نمونه به‌عنوان دادهٔ واقعی ساخته نمی‌شود.

## پیش‌نیازها

- Node.js نسخهٔ ۲۲٫۱۲ یا جدیدتر
- Docker برای PostgreSQL محلی (یا یک PostgreSQL جداگانه)
- npm

## اجرای محلی در Windows PowerShell

۱. فایل محیطی محلی را بسازید و مقدارهای `POSTGRES_PASSWORD` و `DATABASE_URL` را با یک رمز محلی یکسان تنظیم کنید. `SESSION_SECRET` باید تصادفی و دست‌کم ۳۲ نویسه باشد. هیچ‌کدام را در Git ثبت نکنید.

```powershell
Copy-Item .env.example .env.local
```

۲. PostgreSQL را بالا بیاورید، سپس وابستگی‌ها را نصب کنید:

```powershell
docker compose --env-file .env.local up -d db
npm ci
```

۳. migration را صریح اجرا کنید و برنامه را در حالت توسعه بالا بیاورید:

```powershell
npm run migrate
npm run dev
```

برنامه به‌صورت پیش‌فرض روی `http://localhost:3000` در دسترس است. سرویس دیتابیس محلی فقط روی `127.0.0.1:54320` منتشر می‌شود. برای ورود محلی `OTP_PROVIDER=mock` بماند؛ کد تصادفی فقط در رابط توسعه نمایش داده می‌شود و کد ثابتی در پروژه وجود ندارد.

## متغیرهای محیطی

| متغیر | کاربرد |
| --- | --- |
| `DATABASE_URL` | اتصال PostgreSQL برنامه و migration |
| `POSTGRES_PASSWORD` | رمز دیتابیس محلی در Docker Compose |
| `SESSION_SECRET` | کلید HMAC برای هش کد OTP، نشست و محدودیت نرخ؛ حداقل ۳۲ نویسهٔ تصادفی |
| `OTP_PROVIDER` | `mock` فقط در توسعه؛ `parsgreen` برای ارائه‌دهندهٔ پیامک |
| `MAX_UPLOAD_BYTES` | سقف فایل ورودی برحسب بایت؛ پیش‌فرض ۵ مگابایت، بازهٔ ۱ تا ۱۰ مگابایت |
| `PARSGREEN_TOKEN` | توکن وب‌سرویس ParsGreen؛ فقط سمت سرور و فقط وقتی `OTP_PROVIDER=parsgreen` است |

### اتصال OTP به ParsGreen

برای اتصال ParsGreen فقط یک مقدار لازم است: `PARSGREEN_TOKEN`. آن را در پنل ParsGreen، از همان حسابی که نشانی `https://login.parsgreen.com/?Module=WebService` را باز می‌کند، در بخش **WebService** بردارید و در `.env.local` یا بخش Secrets سرویس برنامه قرار دهید. توکن را در چت، Git، مرورگر یا log قرار ندهید.

برای فعال‌کردن ارسال ParsGreen در اجرای محلی، این دو خط را در `.env.local` تنظیم کنید؛ فقط مقدار دوم را با توکن خام پنل جایگزین کنید، بدون پیشوند `Bearer` یا `basic apikey:`:

```dotenv
OTP_PROVIDER=parsgreen
PARSGREEN_TOKEN=YOUR_RAW_TOKEN_HERE
```

تصویر ارسالی از صفحهٔ ۵ راهنمای RESTful، مسیر `POST {baseUrl}/Apiv2/Message/SendOtp` و سه فیلد بدنهٔ درخواست را نشان می‌دهد: `Mobile`، `SmsCode` و `AddName`. برنامه کد OTP را خودش تولید می‌کند و همان کد را برای ارسال و اعتبارسنجی نگه می‌دارد؛ `patternId`، زبان، نوع OTP، امضای SOAP و تنظیمات موفقیت/قالب موبایل در این قرارداد لازم نیستند. شماره در بدنه به قالب محلی ایران (`09…`) تبدیل می‌شود. پاسخ بر اساس `R_Success` بررسی می‌شود.

کد `PARSGREEN_TOKEN` را فقط سمت سرور می‌خواند. SDK منتشرشده با مالک NuGet `parsgreen` برای RESTful API از سرآیند `Authorization: basic apikey:<token>` استفاده می‌کند و نمونهٔ `SendOtp` آن شماره را به قالب `09…` می‌فرستد. چون صفحهٔ احراز هویت PDF فعلی در دسترس نبود، همین قرارداد احراز هویت SDK رسمی به endpoint نسخهٔ ۲ اعمال شده است؛ این تطبیق استنباطی است و با توکن حساب زنده تأیید نشده. یک GET خالی به endpoint روی `login.parsgreen.com` پاسخ `405 Method Not Allowed` با `Allow: POST` داد؛ این فقط وجود مسیر و روش HTTP را تأیید می‌کند، نه اعتبار توکن.

در تولید، اگر `OTP_PROVIDER` تنظیم نشود، برنامه ParsGreen را انتخاب می‌کند؛ هر مقدار لازم یا حساب تأییدنشده باعث خطای امن و غیرفعال‌ماندن ورود می‌شود. برنامه به mock، کد ثابت یا نمایش کد در تولید برنمی‌گردد.

تصویر راهنمای ارسالی: [راهنمای RESTful ParsGreen](https://parsgreen.com/Content/files/Docs/sms/Web-Service/restful-help.pdf). سند SOAP قدیمی با مسیر `SendSMS.asmx` قرارداد دیگری است و مبنای این اتصال نیست. نمونهٔ رسمی SDK در [NuGet ParsGreen.Core](https://www.nuget.org/packages/PARSGREEN.CORE) هم نشان می‌دهد برای RESTful SMS و OTP کلید API استفاده می‌شود.

## پایگاه داده و آزمون‌ها

ساختار در migration نسخه‌بندی‌شدهٔ `db/migrations/0001_initial.sql` است؛ برنامه هنگام شروع، schema را خودکار تغییر نمی‌دهد. migrationها با این دستور به‌شکل تراکنشی اجرا می‌شوند:

```powershell
npm run migrate
```

فرمان‌های موجود:

```powershell
npm run format:check
npm run lint
npm run typecheck
npm test
npm run build
```

تست PostgreSQL فقط وقتی اجرا می‌شود که `TEST_DATABASE_URL` به دیتابیسی با نام شامل `test`، `testing` یا `ci` اشاره کند. این تست یک schema با نام تصادفی می‌سازد و فقط همان schema را حذف می‌کند. از دیتابیس تولید یا دارای اطلاعات واقعی برای آن استفاده نکنید. برای تست کامل پایگاه داده، یک دیتابیس آزمایشی جدا بسازید و همان متغیر را برای فرایند تست تنظیم کنید.

قرارداد endpointها در `docs/openapi.yaml` آمده است. محدودیت‌های حجم، ردیف، صفحه‌بندی، نگاشت داده، تعلق شعبه و مجوزها در سرور نیز اعمال می‌شوند.

## Docker و استقرار

`Dockerfile` یک برنامهٔ Next.js را به‌صورت standalone و با کاربر غیرریشه اجرا می‌کند؛ PostgreSQL در کانتینر برنامه نیست. `docker-compose.yml` فقط برای PostgreSQL محلی است. برای تولید، یک سرویس برنامه به‌علاوهٔ PostgreSQL پایدار جدا در همان پروژه لازم است؛ فایل خام و دادهٔ ماندگار روی فایل‌سیستم کانتینر فرض نشده‌اند. migration باید پیش از دریافت ترافیک، از محیط امنی که `DATABASE_URL` تولید را دارد، یک‌بار اجرا شود:

```text
node scripts/migrate.mjs
```

در Runflare، Dockerfile ریشهٔ پروژه قابل استفاده است و PostgreSQL نیز در فهرست سرویس‌های پشتیبانی‌شده آمده است. CLI رسمی برای ارسال پروژه از `runflare deploy` استفاده می‌کند و در نخستین ارسال مقصد انتخاب می‌شود. [Docker در Runflare](https://runflare.com/%D9%87%D8%A7%D8%B3%D8%AA-%D8%A7%D8%A8%D8%B1%DB%8C-docker/) · [PostgreSQL در Runflare](https://runflare.com/docs/postgres/) · [ارسال با CLI](https://runflare.com/docs/work-with-cli/cli-deploy/) · [ساخت پروژه و تخصیص منابع](https://runflare.com/docs/create-project/)

بررسی عمومی در ۱۸ اکتبر ۲۰۲۶: صفحهٔ Runflare پلن رایگان با ۲ deployment و منابع ۳ گیگابایت RAM، ۱٫۵ گیگاهرتز CPU و ۳ گیگابایت disk را فهرست می‌کند؛ همان صفحه پلن رایگان را مناسب توسعه/آزمایش می‌داند، backup آن را غیرفعال اعلام می‌کند و می‌گوید پس از ۳ ماه حذف می‌شود. نمونهٔ پلن پولی ۲ deployment با ۵۱۲ مگابایت RAM، ۰٫۲۵ گیگاهرتز CPU و ۵۰۰ مگابایت disk و ۲۲۰٬۰۰۰ تومان در ماه را نشان می‌دهد. مستند ساخت پروژه می‌گوید منابع بین برنامه و PostgreSQL تقسیم می‌شوند؛ بنابراین این عددها منابع جداگانه برای هر سرویس نیستند. صفحهٔ Docker برای پلن پولی از ۴ نسخهٔ روزانه، ۱ هفتگی و ۱ ماهانه نام می‌برد. این‌ها اطلاعات عمومی‌اند، نه مشاهدهٔ حساب؛ پلن، هزینهٔ نهایی، شبکهٔ خصوصی، اتصال، storage، restart و امکان بازیابی را پیش از استفاده در پنل همان حساب دوباره بررسی کنید. هزینهٔ مجموع یا مناسب‌بودن یک پلن در این پروژه تأیید نشده است. [پلن‌ها و backup](https://runflare.com/%D9%87%D8%A7%D8%B3%D8%AA-%D8%A7%D8%A8%D8%B1%DB%8C-docker/) · [ساخت پروژه و تقسیم منابع](https://runflare.com/docs/create-project/)

در این محیط CLI و دسترسی حساب Runflare وجود نداشت؛ هیچ پروژه، سرویس یا دیتابیسی ساخته یا deploy نشده است. برای deploy واقعی، مقصد را در CLI/پنل بازبینی کنید، secretها را در تنظیمات امن وارد کنید، اتصال داخلی برنامه به PostgreSQL را تنظیم کنید، migration را پیش از ترافیک اجرا کنید و وضعیت `/api/health` و backup/restore را از پنل خود تأیید کنید. دیتابیس را برای دسترسی عمومی باز نکنید. تا زمانی که backup و restore واقعی آزموده نشده، فقط به ادعای صفحهٔ عمومی تکیه نکنید.

## یادداشت فنی

- برنامه: Next.js و React با TypeScript سخت‌گیر؛ API و UI در یک سرویس Node.js.
- ذخیره‌سازی: PostgreSQL، migration SQL صریح، queryهای پارامتری و قیدهای مرکب برای جلوگیری از اتصال دادهٔ دو شعبه.
- مبلغ: اعداد صحیح ریال در PostgreSQL `bigint`؛ فایل تومان هنگام ورود به ریال تبدیل می‌شود.
- فونت: Vazirmatn از بستهٔ خودمیزبان Fontsource، با مجوز SIL Open Font License.
- امنیت: محدودیت درخواست OTP، کد HMACشده، انقضا/تلاش محدود، کوکی HttpOnly/SameSite، بررسی same-origin، محدودکردن داده به شعبه و ثبت audit.
- فایل‌ها: CSV با UTF-8 و XLSX؛ فایل اصلی نگه‌داری نمی‌شود و متن خانه‌ها پیش از خروجی صفحه‌گسترده در برابر تزریق فرمول محافظت می‌شود.
